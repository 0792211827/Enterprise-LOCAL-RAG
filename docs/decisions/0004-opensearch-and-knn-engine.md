# ADR-0004: Keep OpenSearch; the nmslib kNN engine is a known trade-off (engine decision superseded)

- **Status:** OpenSearch retention accepted. The engine decision is **superseded by [ADR-0001](../adr/0001-document-restrictions-and-lucene-knn.md)**: new indices use `lucene`, and existing ones move with `make reindex`. Seeded narrow-scope recall (live OpenSearch 2.19, 40 chunks in a 4,040-chunk index, recall@10): nmslib 0.10, lucene 1.00 (`backend/tests/integration/test_narrow_scope_recall.py`).
- **Context:** All chunks live in one hybrid index (BM25 + kNN, fused by an RRF search pipeline), tagged `knowledge_base_id`. The kNN field uses the `nmslib` engine, which applies filters as **post-filters**: ANN returns the global top-k, then the KB filter discards the rest, so a narrowly scoped search can under-return. `KNN_FILTER_OVERSAMPLE=10` and `KNN_MAX_CANDIDATES=1000` mitigate this (`services/opensearch/client.py`). It cannot leak data across KBs.
- **Decision:** Keep OpenSearch (no vector-database catalogue). ~~Keep nmslib for now.~~ (superseded, see status)
- **Was open (now resolved by ADR-0001):** moving to `lucene` or `faiss` (efficient pre-filtering) requires a new index and a reindex with an alias swap. It should happen before document-level ACL tags (roadmap Phase 12), where filter selectivity is higher. Tied to the embedding-dimension work (roadmap Phase 2), since both change the mapping.
- **Consequences:** retrieval quality under narrow scopes is not benchmarked yet. Add a seeded recall test before changing the engine.
