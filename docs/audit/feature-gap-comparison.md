# Feature gap comparison: Open WebUI vs. Enterprise-LOCAL-RAG (Phase 3)

*Combines `current-architecture-gaps.md` (Phase 1),
`openwebui-reference-notes.md` (Phase 2) and
`hardware-backend-reference-notes.md` (Phase 2b). OWUI is at commit `8bd8b4f`;
ours is `feature/owui-gap-analysis` at `d2d90c7`.*

**Legend**
- **Track:** 🔒 Security (context gaps #1–4) · ⚙️ Hardware/Backend (#7–8) · ○ Optional (#5–6)
- **Effort:** S ≈ ≤ 2 days · M ≈ 3–7 days · L ≈ 2+ weeks, for one engineer, including tests
- **Breaking risk** assumes the plan's rule that every feature ships **off by default** and preserves today's open behaviour. The risk rating covers what could break *when an operator turns the feature on*, or for work that can't be flagged.

## Security track 🔒

| # | Feature | Open WebUI approach | Our current state | Gap severity | Effort | Breaking risk |
|---|---------|---------------------|-------------------|--------------|--------|---------------|
| S1 | **Identity intake / SSO** | OWUI is the identity provider. It uses Authlib OIDC login (one generic provider plus presets), maps claims to a local user, role and groups, and then **issues its own HS256 JWT**, never re-validating the IdP token. It also supports trusted-header login, LDAP, SCIM and token exchange. | Nothing. No route receives an identity, the only middleware is CORS, and traces hardcode `user_id="api_user"`. | **Blocker** | **M** | **Low.** It's a new `AUTH__MODE`, default `disabled`, which gives an anonymous principal with all roles, so behaviour is identical to today. The risk is limited to misconfiguration once enabled (wrong issuer or audience locks everyone out); a clear startup validation error mitigates that. |
| S2 | **RBAC on API routes** | Three fixed string roles (`admin`/`user`/`pending`) checked through `Depends(get_admin_user)` / `get_verified_user`. Group feature permissions are OR-merged with the defaults. Admin checks are scattered inline across routes. | None of the 42 routes has a role gate. The admin CRUD routes, including provider `/test` and `/models`, which make the backend call caller-supplied URLs (SSRF), are open to anyone who can reach the port. | **Blocker** | **S–M** | **Low.** Router-level `dependencies=[require_role(...)]` has no effect in `disabled` mode. When enabled, the admin UI needs a token (see F1), so it is effectively coupled to the frontend work. |
| S2a | ↳ **Enforce per-application API keys** | Per-user keys, stored in **plaintext**, off by default. `expires_at` isn't enforced. | Keys are minted and hashed, with rotate and revoke, but **not enforced** on `/v1/chat/completions`. Even when a key is presented it isn't checked against the application being called. | **Blocker** (the key is advertised in the UI but is not a real control) | **S** | **Low.** A flag, `API_KEYS__ENFORCE=false` by default. When turned on, clients that don't send a key will start getting 401, which is the point, and should be documented. |
| S3 | **Permission-aware retrieval (KB level)** | Owner plus an `access_grant` table (user/group/anyone × read/write). The caller's access is **re-checked at every retrieval**, and a KB the caller can't read is silently dropped even when it is attached to a model. Isolation is per collection. Unknown scope is denied. The admin bypass is inconsistent. | Only the application path scopes to the application's KBs (and it fails closed if there are none). **Legacy `/ask`, `/stream`, `/hybrid-search` and `/ask-agentic` search every KB.** No grant data exists. The Redis cache key has no scope, so a cached answer would leak across permission boundaries. | **Blocker** (the core differentiator) | **M** | **Medium.** It adds a new `knowledge_base_grants` table, a single scope resolver used at 5 call sites, and a scope hash in the cache key. It's off by default, where the resolver returns ALL, so there is no change. When enabled, legacy endpoints stop returning unpermitted KBs, which is intended, but any client that relied on global search will see fewer results. The cache key change invalidates existing cache entries once, which is harmless. |
| S3a | ↳ **Document-level ACL tags** | **Absent.** OWUI has no chunk or document permission filter. | Absent. The shared index already filters by term, so adding a tags filter is structurally easy. It is complicated by the nmslib post-filter. | **Important** (a differentiator OWUI doesn't have, but KB-level covers most buyers first) | **M–L** | **Medium.** It needs an additive `PUT _mapping`, a side table for tags, and ingest changes. Untagged chunks fall back to KB-level permission. Filter selectivity may require the kNN engine switch (a reindex), which should be a separate, explicit decision. |
| S4 | **Structured audit log** | An HTTP middleware writing a loguru JSON-lines file. **Off by default, and chat/RAG paths are excluded by default.** It captures user, IP, verb, URI and bodies truncated to 2 KB. There is **no DB table, no query/export API, no UI and no retrieval facts.** `chat_message.sources` is the de facto (mutable) record. | Only Langfuse, which is optional, async and silently lossy, and attributes every request to `"api_user"`. **The application path (playground plus `/v1`) isn't recorded at all.** No chunk IDs, source IP, cache-hit flag or admin-action trail. | **Blocker** | **M** | **None to low.** New `audit_events` table, a recorder, an admin read/export API and a request-ID middleware. `AUDIT__LEVEL=off` by default. The answer functions gain an optional parameter. One INSERT per request is negligible next to generation. |
| S5 | **Perimeter hardening** *(found in Phase 1; not in the original list)* | The same exposure exists when it is deployed with an external vector DB. The docs recommend a reverse proxy. | Every compose service publishes to `0.0.0.0`, including Postgres, OpenSearch (with its **security plugin disabled**), Redis and Ollama. API-level RBAC can be bypassed by querying OpenSearch directly. | **Important.** It's what makes S1–S4 meaningful, but it's deployment config, not code. | **S** | **None.** An opt-in `compose.hardened.yml` overlay binds infrastructure ports to the internal network only. `compose.yml` stays untouched, following your Phase 5 rule. |

## Hardware/Backend track ⚙️

| # | Feature | Open WebUI approach | Our current state | Gap severity | Effort | Breaking risk |
|---|---------|---------------------|-------------------|--------------|--------|---------------|
| H1 | **OpenAI-compatible backends** (vLLM, TGI, llama.cpp-server, SGLang, NIM) | No backend-specific code at all (no vLLM, TGI or TensorRT paths). Everything is an "OpenAI connection" with N base URLs. The only special-casing is llama.cpp and LM Studio model load/unload. | `OpenAICompatibleLLMProvider` exists and the factory accepts `LLM__PROVIDER=vllm`. It is **not verified** against real servers. Known risks: the system prompt is folded into a user message, health checks depend on `/models`, and there is no `max_tokens` default (TGI's historic default was 20 tokens). | **Important** (a deployability blocker for NVIDIA-heavy buyers, but most of it is verification) | **S** | **None.** Documentation, an example compose overlay, `.env` snippets, and small provider fixes that don't affect the Ollama default. |
| H2 | **Inference backend abstraction: all paths use it** | A dispatcher over two wire protocols (Ollama native and OpenAI-compatible), with Ollama responses normalized to OpenAI format. There's no Python interface class. | There is a **real `LLMProvider` ABC**, which is better than OWUI's, but **only the application path uses it**. `/ask`, `/stream`, all four agentic nodes (`ChatOllama`) and `/health` are hardwired to Ollama, so with `LLM__PROVIDER=vllm` those endpoints still need Ollama running. | **Important** | **M** | **Low.** The Ollama default produces identical behaviour. Agent-node fixtures and `test_wiring_regressions.py` need updating to the new seam; that is a signature change, not a behaviour change, and will be explained in the commit. |
| H2a | ↳ **Honour per-application provider and endpoint** | Per-connection model routing (a model ID maps to a connection index, with random load balancing across Ollama nodes). | `ModelConfiguration.llm_provider` and `llm_endpoint` are collected by the UI and **ignored at runtime**, so an application "configured for vLLM" silently uses the global provider. | **Important.** The UI currently promises something the backend doesn't do. | **M** | **Low.** Existing rows default to `ollama` with a null endpoint, which falls back to the global provider, so behaviour is unchanged. |
| H3 | **GPU detection and configuration** | No GPU inventory. A torch device (cuda/mps/cpu) is picked only for in-process embedding and reranking models. A `docker-compose.gpu.yaml` overlay reserves GPUs **on the Ollama service**, with an AMD/ROCm variant and a launcher script that sniffs `nvidia-smi` or `lspci`. The UI shows no hardware. | **No GPU is passed to any container.** Ollama on a Linux GPU host runs on CPU. `/system/gpu` exists and the UI polls it, but it runs `nvidia-smi` **inside the API container**, which has no GPU or driver, so it reports "unavailable" everywhere. The API image ships unused CUDA torch wheels (several GB). | **Important.** The compose overlay is the real blocker; the display is nice-to-have. | **S** (overlays + VRAM residency from Ollama `/api/ps`) | **None.** Opt-in overlay files. `GPUResponse` only gains optional fields. |
| H4 | **Quantized model support** | Delegated to the backend. The only explicit piece is an admin-only "download or upload a GGUF and register it with Ollama" helper, which fetches from HuggingFace or GitHub. The UI displays quantization level. | GGUF **works today** through Ollama (library tags plus a Modelfile import). AWQ, GPTQ and FP8 need vLLM, TGI or SGLang, so they come free with H1. Quantization level isn't displayed. | **Nice-to-have** (covered by H1 plus documentation) | **S** | **None.** Documentation, plus optionally displaying `details.quantization_level` from `/api/tags`. We shouldn't copy the upload/download helper because it conflicts with no-external-calls and adds a large upload surface. |
| H5 | **Embedding dimension config** *(found in Phase 2b)* | Their OpenSearch implementation sizes the index from the first vector. | The index mapping **hardcodes 1024**. `OPENSEARCH__VECTOR_DIMENSION` exists but nothing reads it. Swapping to a non-1024-dimension embedding model via config makes every bulk index fail. | **Important** (it undermines "swap embedding provider by config") | **S** | **Low.** Build the mapping from config and add a startup or ingest guard for a dimension mismatch. An existing index keeps working; changing dimension on existing data is inherently a reindex, which the guard makes explicit. |
| H6 | **Multi-connection model catalogue / vector-store abstraction** | Merged model list across N connections, plus a `VectorDBBase` ABC with 13+ vector databases. | One endpoint per provider kind. OpenSearch is concrete and there is no vector-store interface. | **Nice-to-have.** Buyers standardize on one inference server, H2a covers per-application needs, and OpenSearch hybrid search is a product choice. | **L** | **Medium** if attempted (a broad refactor). Recommend deferring. |
| H7 | **New native adapters** (llama-cpp-python in-process, raw Triton/TensorRT-LLM) | OWUI has none. llama.cpp is reached as an OpenAI-compatible server, and TensorRT through NIM or `trtllm-serve`. | None. | **Nice-to-have.** Only if a buyer mandates raw Triton; H1 covers llama.cpp and TensorRT via their OpenAI-compatible servers. | **L** | **Medium.** Native builds and model memory would sit inside the API process. |

## Optional / future ○ (scope only, not planned for build)

| # | Feature | Open WebUI approach | Our current state | Gap severity | Effort | Breaking risk |
|---|---------|---------------------|-------------------|--------------|--------|---------------|
| F1 | **Admin UI auth** *(needed if S1/S2 are enabled)* | The SPA holds OWUI's JWT (a cookie that isn't httponly after OAuth login) and has login pages. | No user, token or role concept. Every call goes through `lib/api/client.ts`, so attaching a token is a one-file change. | **Important *once* S2 is enabled** (otherwise the admin UI gets 401s). A minimal version is part of S2's rollout, not a separate product. | **S–M** | **None** when `disabled`. Minimal version: an optional OIDC PKCE login or a pasted token, sending `Authorization`, handling 401/403, and showing a role badge. |
| F2 | **End-user chat UI** | OWUI's core product: a full chat app with history, sharing, folders and multiple models. | Only the admin playground. End users reach us through the host app's own UI via `/v1/chat/completions`. | **Nice-to-have.** Buyers embed us behind *their* UI; a chat UI competes with OWUI on its home turf. | **L** | **None** if built as a separate app. Not recommended now. |
| F3 | **Plugin / tool extensibility** | Admin-uploaded Python "Tools", "Functions" (pipes, filters, actions) and "Pipelines", **executed in-process** with the server's privileges, plus MCP tool servers. | None. The agentic graph has one fixed retriever tool. | **Nice-to-have.** In-process arbitrary Python conflicts with a regulated-buyer security story; if ever built, it should be out-of-process (MCP) and audited. | **L** | **Medium to high** (a new code-execution surface). Not recommended now. |

## Proposed priority order (for your confirmation)

**Security track** (sequential, because each step builds on the previous):

1. **S1 Identity intake**, with the request-ID middleware and the `Principal` dependency
2. **S2 RBAC + S2a API-key enforcement**, with the **F1 minimal admin-UI token** support so enabling RBAC doesn't lock out the admin UI
3. **S3 Permission-aware retrieval (KB level)**, including cache-key isolation
4. **S4 Audit log.** It could reasonably move ahead of S3, because it's lowest-risk and immediately demoable, and its schema already has the permission-decision fields (`permitted_kb_ids`, `dropped_kb_ids`) ready for S3 to fill in.
5. **S5 Hardened compose overlay** (small, can ride alongside any step)
6. *Later:* **S3a Document-level ACL tags**

**Hardware/Backend track** (parallel, staffed and estimated separately):

1. **H1 OpenAI-compatible backend verification** (vLLM first), plus **H4** documentation
2. **H3 GPU compose overlays** plus VRAM residency in the `/system/gpu` UI
3. **H5 Embedding dimension from config**
4. **H2 All paths through `LLMProvider`**, then **H2a per-application provider**
5. *Deferred:* H6, H7

**Scoped only:** F2, F3.

## Decisions I need from you before Phase 4

1. **The order above.** In particular, should **S4 (audit) go before S3 (retrieval permissions)**?
2. **Grants key:** should grants key on **IdP group or role claim values** (recommended, since we don't own users), or do you want a local users/groups table as well?
3. **Identity modes for v1:** **JWT/JWKS bearer plus trusted-header** (recommended), or JWT only?
4. **F1 scope:** is minimal admin-UI token support acceptable as part of S2? It's the only way to enable RBAC without locking out the admin UI.
5. **S5:** should the hardened compose overlay be in scope? It's a new file only; `compose.yml` is untouched.
6. **Migrations:** all proposed tables are *new*, so `create_all` handles them with no Alembic needed yet. S3a (document tags) is also designed around a side table. Do you want Alembic introduced now anyway, as a baseline revision, to future-proof column changes?
